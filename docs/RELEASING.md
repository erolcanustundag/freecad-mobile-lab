# Publishing verified native milestones

The version-stamped publisher in `scripts/release_publisher.py` and workflow in `docs/ci/publish-full-release.template.yml` preserve the small-branch publication path used for 1.23. Update their exact version/tag/owned-branch assertions together when preparing a later milestone. They run only in the expected repository and publication branch, with the built-in GitHub Actions token.

1. Select a new version/code before application edits. Qualify four bounded native workflows, run the relevant JNI/cold-restoration and existing regressions, build/sign the compatible APK, and run static APK/core verification. Seal all application inputs. Keep physical Android execution and full desktop/workbench parity statuses explicit.
2. Package the APK, native runtime, frozen corresponding sources and public application sources. Verify all input/file hashes and CRCs. Await packaging completion before syncing the final source commit. Save the APK and private recovery checkpoint separately. Keep keys and private continuation out of Git/public assets. Require successful source CI on the exact sealed commit.
3. Compress the APK into a ZIP containing only its filename, split the three changing public assets into 1 MiB chunks, and upload them as Git blobs. Verify each returned Git blob SHA1 against its exact bytes. The transport manifest records every part name/blob SHA, assembled transport size/SHA256 and final file size/SHA256; frozen sources may use a pinned prior public release URL. The manifest's `source_commit` is the sealed application commit.
4. Put only the manifest, publisher and version-stamped workflow in the temporary publication branch. Do not add hundreds of binary chunks to that branch: large-tree/ref updates can time out or fail. The publisher reads exact public Git blob objects through authenticated REST/base64, checks each blob, then verifies assembled transports, APK extraction, all final file hashes and ZIP CRCs. It uses at most six concurrent chunk reads and a bounded part count.
5. Persist a transport receipt before creating/updating the owned ref. Preserve unrelated branches and main. If a ref mutation fails or times out, inspect the actual ref/release/workflow state before another mutation. A successful object-creation response does not establish that a branch points to it. Generic text-fetch tools reject binary blobs; the Actions publisher uses the actual REST blob JSON/base64 API.
6. The publisher creates or resumes only the matching draft/target commit, verifies all four uploaded asset sizes/digests, publishes with draft=false/prerelease=false/latest=true, checks the source tag and removes only its exact owned branch/GITHUB_SHA. It refuses to replace mismatching assets of a published release.
7. Independently verify the full/latest release, tag commit, all four remote asset names/sizes/digests, successful source/publication CI and HTTP404 for the owned temporary branch. Save publication evidence in `docs/GITHUB-PUBLICATION.json` and update the asset lock's publication status. Sync the proof and recovery notes; check final source CI and unchanged sealed application inputs.

Native libraries and source archives have independent hashes. An unchanged native DLL does not establish Android execution of new Python/UI workflows. Retain the compatible private signing identity for upgrades; dedicated production-key migration remains separate work. Current desktop/Gui/Assembly/Rhino parity and F-Droid gates remain incomplete.
